### Demo sealing: remaining race

`js/file-system-race` at `demos/quantum-enchantments/verify-demo.mjs:98` points
back to the exclusive open at line 92. The tool creates a randomly named file
with `wx`, writes and flushes it, closes it, reads it back by pathname, and then
renames it over the manifest.

Exclusive creation prevents overwriting an existing temporary file, but it does
not prevent a writer with access to the directory from changing that pathname
after validation. A deterministic I/O-interference probe in a disposable fixture
changed the temporary bytes after readback; those changed bytes became the
manifest. This was a fault-injection reproduction, not a live concurrent-process
exploit. The CLI's subsequent verification can detect inconsistent content but
cannot restore the previous manifest after replacement.

**Operational boundary:** seal only in a trusted, quiescent package directory,
without concurrent editors or another sealer. This is local maintainer tooling,
not a browser-runtime or remote roleplay-input path. It is not safe to describe
the sealing operation as a transaction over adversarial/concurrent filesystem
changes. Follow-up hardening should avoid pathname reopening where possible and
address ownership through replacement, without claiming that descriptor reads
alone solve all rename or package-input races.

The `js/user-controlled-bypass` finding at line 110 concerns the
`process.argv[1]`/`import.meta.url` entrypoint guard. It selects direct CLI
execution, not user authorization. The explicit `--seal` operation remains
subject to ordinary filesystem permissions. Keep the guard to avoid executing
the CLI when its helpers are imported.
